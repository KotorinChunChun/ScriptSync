## 既存Web側の仕様（要求の追加ではなく調査結果）

参照：連携先の `dev/exchange-format-spec.md`、`dev/desktop-import-request.md`、`exchange.mjs`。

- 交換形式は `scriptsyncweb-exchange-1`。ZIP内の `project.json` が正本で、分割前原稿、本文と順序を持つ行、各行のテイクを保持する。台本だけの場合は `takes=[]`、`selected=null` を使用できる。
- 現行形式は単一の原稿を保持する。新規Web出力は `.md` の `sourceFileName` と `scriptPath` を持つ。旧ZIPのファイル名省略は許容する。ファイル名は参考情報であり、行の照合キーは本文と行順。
- 行番号は空行除外・句点分割後の順序で、デスクトップ原稿の物理行番号と一致するとは限らない。
- 音声はPCM16・48kHz・1/2chのWAV。SHA-256は出力WAV全体を対象とする。Web側の手動編集では同じtake IDのハッシュが変わる。
- `take.original` は編集前音声の復帰用データで、独立テイクではない。Webの採用情報や採用のみZIPは、既存採用の上書き・既存テイクの削除指示ではない。
- ローカルZIPは非暗号化。サーバー保存ZIPはAES-256と6桁キー。対応範囲はQ003で確認する。
- Web仕様の上限は音声合計100MiB、ZIP100MiB、JSON4MiB、5000エントリー。実装計画時にパス・重複エントリー・展開サイズ・実音声・ハッシュの検証を具体化する。

## WASAPI警告のコード調査

`crates/scriptsync-recorder/src/windows/wasapi_capture.rs` の `observe_packet` は、OSの不連続フラグまたはデバイス位置の欠落があれば不連続と判定する。`record_packet_observation` は該当パケットごとに1回加算する。同じパケットで両条件が成立しても二重加算する構造ではない。先行パケットがない最初のパケットでもOSフラグがあれば1回となり、欠落数は比較できず0になる。

`src-tauri/src/app.rs` は不連続回数が1以上なら欠落0でも「要確認」にする。表示された0は欠落を計数できていない場合も含むため、音声欠落がなかったことの保証ではない。今回のユーザー環境の発生時点・音声・パケットログは未検証で、開始時フラグが原因とはまだ確定しない。

Microsoft資料では不連続フラグはストリーム状態遷移やタイミング異常でも発生し得るとされる：[AUDCLNT_BUFFERFLAGS](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-_audclnt_bufferflags)。

## 連携情報と調査上の留意点

- 過去のユーザー指定記録のMicrosoft EntraテナントID：`a0fa18d4-3880-44a4-b5b2-bf59e18d7fc2`。今回クラウド上の状態は未照会。クライアントID・リダイレクトURI・会社の管理ポリシー・送信先フォルダーは別途確認する。
- Web側の `dev/docs/CLOUD_DRIVE_AUTH_SETUP.md` は個人MicrosoftアカウントとGoogle Drive向けの旧準備案。今回の会社OneDrive・Boxの要件へそのまま適用しない。Boxの登録情報は今回参照した資料にはない。
- Webの `app.js` には暗号化ZIPの分割送信処理がある。デスクトップからの送信・スマートフォン側での取得導線は、既存APIとの互換性を設計時に確認する。QRコードによるWeb起動だけでは台本の受け渡し完了を意味しない。
- 2026-09-12のローカル `codex exec --help` には画像添付とプロンプト・構造化出力の指定はあるが、音声専用添付オプションは確認できなかった。CLIへのファイルパス指定だけで音声認識可能とは断定しない。音声認識ツールを介する場合は、使用エンジン、外部送信、費用・認証の条件を区別する。
- 調査資料：[Codex CLI公式資料](https://learn.chatgpt.com/docs/developer-commands?surface=cli)、[音声認識APIのモデル例](https://developers.openai.com/api/docs/models/gpt-4o-transcribe)。API直接利用は追加候補であり、Codex CLI方式の代替として無断で置き換えない。

本文や行順だけで対応が一意に決まらない音声は、既存の差分・行対応付け操作との関係を整理してから確定する。未承認行や対応先がない音声を黙って破棄・別発話へ追加しない方針を提案する。

# ScriptSyncのリリース確定

## 対象を確定する

[AGENTS](../../../AGENTS.md)、[README](../../../README.md)、[開発者ガイド](../../../docs/DEVELOPERS_GUIDE.md) と対象版のimp・taskを読む。作業ブランチ名、アプリの実装版、次版の計画を区別する。計画の存在は次版実装やデータ移行の許可ではない。

Gitの状態、差分、現在ブランチ、既存タグとコミットの関係を確認する。ユーザー指定の版をpackage.json・package-lock.json・src-tauri/Cargo.toml・Cargo.lock・tauri.conf.jsonと照合する。版を上げる指示がなければ変更しない。

## 検証と成果物

1. [変更検証](../scriptsync-project-validation/SKILL.md)に従い、未検証の変更へ必要な試験を実施する。文書のみの確定で既存結果を使う場合は検証対象コミットと今回の差分を照合し、再実行とは記載しない。
2. 最新実行ファイルが必要ならルートで `npm run tauri build -- --no-bundle` を実行する。成果物は `src-tauri/target/release/scriptsync.exe`。ビルド成功後に存在・更新日時・SHA-256を確認する。
3. 使用中EXEの上書き拒否はコンパイル失敗と区別する。録音・未保存データを確認せずプロセスを強制終了しない。アプリの安全な終了か別出力先など、現在の操作状態と許可範囲に応じて解決する。
4. 起動を依頼された場合、ビルド済みの対象EXEを起動し、起動プロセスと画面を可能な範囲で確認する。開発サーバーや旧プロセスが動いているだけで最新アプリの起動確認としない。

## Gitと記録

- 関連差分だけを明示的に追加し、日本語でコミットする。dev/sample、個人原稿・録音、認証情報、生成物を一括追加しない。
- 完成ブランチに必要な修正が含まれるか祖先関係を確認する。fast-forward可能ならそれを使い、競合・別作業がある場合は履歴を失う強制更新をしない。
- 既存リリースタグを移動しない。新しい確定タグが必要ならユーザー指定と既存命名を確認し、未使用名へ作成する。ローカル確定をpush・公開配布の許可とみなさない。
- 対象版のimp・taskとリリース記録に、コードの確定点、成果物パスとハッシュ、試験の実施条件、未実機確認、起動の有無を残す。最終的な文書コミットのIDはコミット後に確認し、文書内に未確定のIDを書かない。
- 次版へ進む指示があるときだけ旧版文書をhistoryへ保存し、新版の要求・計画・進捗を用意する。過去のリリース記録の試験結果を書き換えない。

完了報告では版・ブランチ・コミット・タグを実際のGitと照合し、ビルド、起動、実機音質、公開を区別する。スキルを読んだだけでこれらを実行済みにしない。
